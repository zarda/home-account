# The translation catalog

Three locales — `en`, `ja`, `tc` — live in `src/assets/i18n/*.json`, ~1,175
leaf keys each. `TranslationService.t()` resolves a dotted key against the
loaded dictionary and **returns the key itself on any miss**; loading a locale
replaces the whole dictionary, so there is no English fallback. A missing or
misspelled key is therefore silent in tests and visible in the UI, as raw text
like `import.noTransactions`. Everything below exists to make that class of
defect fail a gate instead of shipping.

The reasoning and the rejected alternatives are in
[ADR 0036](ADR/0036-a-user-facing-string-lives-in-the-catalog.md).

Strings are only half a language. Dates and numbers follow the chosen
language too, through their own chokepoint — see
[locale-formatting.md](locale-formatting.md). So does layout direction: each
`Language` entry declares its own `dir`, and every locale shipped today is
`ltr` — see [rtl.md](rtl.md) for what a right-to-left one would need.

## The catalog and its shapes (#272)

A leaf is a string, or a **plural object**: members named after the CLDR
cardinal categories (`zero`, `one`, `two`, `few`, `many`, `other`), each a
string. `t()` selects a member with `Intl.PluralRules` for the active locale
when the params carry a numeric `count`, falls back to `other`, and
interpolates as usual — `{{count}}` stays in every member, so the `one` form
renders "1 transaction shown". A plural entry reached without a numeric
`count` returns the key: the same loud miss as any other non-string leaf.

**Only English declines.** ja and tc have no number agreement; their entries
stay plain strings, byte-identical at every count. Locale parity is asserted
on the bare leaf path (`aiSearch.matchCount`, whatever its shape), and
`translation-keys.spec.ts` derives each locale's permitted member set from
`Intl.PluralRules(...).resolvedOptions().pluralCategories` — en must carry
exactly `one` + `other`, and a pluralized entry in ja or tc is a failure by
construction.

The member names are **reserved words**: a genuine namespace whose keys were
all category names would be read as a plural leaf. None exists; the shape
check names any that appears.

Twenty-three keys carry members today — every key where a count of 1 is
reachable and the sentence has a noun that agrees: `transactions.
resultCountAnnouncement`, `budget.alertSnackbarMore`, nine under `settings.*`
(preview/import/restore/delete counts), `aiSearch.matchCount`, seven under
`import.*`, and four under `insights.*`. Count keys guarded to `> 1`, fed a
compile-time constant, or floored at ≥2 by a detector stay plain strings — if
the guard changes, the key converts then.

## How a string gets checked (#260)

`npm run i18n:check` (`scripts/check-i18n.mjs`, a CI step) runs a self-test of
its own parser first, then three scans:

1. **Balanced `t(` calls.** The first argument of every `t(` call is walked
   character-by-character — paren depth, quote state — to the first top-level
   comma or the balanced close, across newlines. Every dot-namespaced quoted
   literal in it must resolve in all three locales; the dot rule keeps a
   ternary's comparison literal (`'expense'`) from being taken for a key. A
   first argument with no key-shaped literal (`t(chip.labelKey)`, template
   literals) is dynamic: counted, never failed. This is what the per-line
   regex could not do — #260 shipped inside a `t(` split across lines with a
   ternary argument, invisible even to a multi-line regex.
2. **Pipe keys.** `'some.key' | translate` stays a line-based scan; a pipe
   whose left side is not an adjacent literal counts as dynamic.
3. **Static aria-labels** — below.

The unit suite adds what the checker cannot see: `translation-keys.spec.ts`
asserts cross-locale parity, plural member shape, non-empty values, and
placeholder parity (union across plural members). Neither gate can check a
dynamic key's existence, a commented-out call is still counted as a
reference, and English hardcoded as *visible text* in a template is caught by
nothing but review and the component specs that pin sentinel translations.

## Accessibility labels (#273)

`aria-label` wins the accessible-name computation outright — a translated
tooltip does not help a screen-reader user if the label next to it is
hardcoded English. The checker rejects any literal `aria-label="…"` under
`src/app` templates. Three forms pass:

```html
[attr.aria-label]="'common.moveUp' | translate"   <!-- the convention -->
[aria-label]="someExpression"
aria-label="{{ 'some.key' | translate }}"
```

The convention's model is `camera-capture.component.html`, which binds
`common.moveUp` / `common.moveDown` / `common.remove` on its reorder trio.
The UI-audit harness must never select on label text — it drives the user
menu via `app-header button.user-menu-button`, a class that exists for that
purpose, locale-independent by construction.

## Summary

| Escape route | What closes it | Where |
|---|---|---|
| Key referenced that no locale defines | balanced `t(` + pipe scans | `npm run i18n:check`, CI |
| Key in one locale, missing in another | path parity | `translation-keys.spec.ts` |
| English plural forced on a count of 1 | plural objects, en only | `t()` + the 23 converted keys |
| Plural members malformed or misplaced | per-locale CLDR shape check | `translation-keys.spec.ts` |
| Placeholder added to en alone | placeholder parity (member union) | `translation-keys.spec.ts` |
| Hardcoded `aria-label` | static-aria scan | `npm run i18n:check`, CI |
| Checker's own parser drifting | 20-case `--self-test` | chained into `i18n:check` |
| Hardcoded *visible* English text | nothing automatic | review + sentinel specs |

## When you add another string

**A new user-facing string?** Give it a key in all three files — parity fails
on a partial add — and bind it with `| translate` or `t()`. If it names a
control only assistive tech hears, it is an `[attr.aria-label]` binding, not
an attribute.

**A new counted string?** Ask two questions before pluralizing: can the count
actually be 1 (check the guard), and does the English sentence have a noun
that agrees? Both yes → en gets `{ "one": …, "other": … }` with `{{count}}`
in both members; ja and tc get one plain string each. Either no → three plain
strings.

**A new `t()` call?** Write the key as a literal in the first argument if you
can — the checker validates it wherever the line breaks fall. A computed key
is invisible to every gate; if you must, add a spec that resolves it against
the real catalogs, the way `insight-card.utils.spec.ts` does.

**Removing or renaming a key?** `i18n:check` lists every referencing site,
including commented-out ones. Rename in all three files and every site in one
commit; the gates fail on anything left behind.
