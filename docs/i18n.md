# The translation catalog

Three locales — `en`, `ja`, `tc` — live in `src/assets/i18n/*.json`, ~1,830
keys each (en's plural entries add their members as leaves, ~1,880 there).
`TranslationService.t()` resolves a dotted key against the loaded dictionary
and **returns the key itself on any miss**; loading a locale replaces the whole
dictionary, so there is no English fallback. A missing or misspelled key is
therefore silent in tests and visible in the UI, as raw text like
`import.noTransactions`. Everything below exists to make that class of
defect fail a gate instead of shipping.

The reasoning and the rejected alternatives are in
[ADR 0036](ADR/0036-a-user-facing-string-lives-in-the-catalog.md).

Strings are only half a language. Dates and numbers follow the chosen
language too, through their own chokepoint — see
[locale-formatting.md](locale-formatting.md). So does layout direction: each
`Language` entry declares its own `dir`, and every locale shipped today is
`ltr` — see [rtl.md](rtl.md) for what a right-to-left one would need.

None of that touches what a user typed: translating a stored note into the UI
language on demand is a different feature with a different service, described
in [translation-lens.md](translation-lens.md).

## Which language a session speaks

At boot, `TranslationService.init()` asks `mapLocaleTag(navigator.language)` —
a lowercased prefix match, `zh*` → `tc`, `ja*` → `ja`, `en*` → `en`, anything
else `null` — and falls back to `en` when that is null. The result is kept as
`detectedBrowserLocale`, because "asked for English" and "asked for something
we do not ship" are different answers that `currentLocale()` alone collapses
into one.

Once a profile loads, **the account outranks the device**: the preferences-sync
effect in `AuthService` calls `syncFromDatabase(preferences.language)` whenever
`currentUser` changes, which is the same path a Settings change takes.

A **newly created** account is seeded with `detectedBrowserLocale`, falling
back to `en` — `buildNewUserProfile` takes the language and spreads it over
`DEFAULT_USER_PREFERENCES`, which itself keeps `language: 'en'` as the
resolver-neutral fallback. The device's own answer rather than
`currentLocale()`, so that signing out and signing a second person in without
a reload does not write the departing user's chosen language into the new
account. (The never-persisted fallback profile of a degraded session is the
one exception: it keeps `currentLocale()`, because its whole job is to leave
the UI where it already is.) If the device named a language we ship no catalog
for, an interactive Google sign-in gets one more chance: the account's own
`locale`, mapped by the same `mapLocaleTag`, patched in after the profile
exists. On native that locale comes from the Capacitor plugin's
`additionalUserInfo`, whose `profile` map is not guaranteed to carry the key —
when it does not, the account keeps the boot fallback. The reasoning is in
[ADR 0076](ADR/0076-the-welcome-replays-on-request-and-a-first-login-speaks-the-browsers-language.md).

## The catalog and its shapes (#272)

A leaf is a string, or a **plural object**: members named after the CLDR
cardinal categories (`zero`, `one`, `two`, `few`, `many`, `other`), each a
string. `t()` selects a member with `Intl.PluralRules` for the active locale
when the params carry a numeric `count`, falls back to `other`, and
interpolates as usual — `{{count}}` stays in every member, so the `one` form
renders "1 transaction shown". A plural entry reached without a numeric
`count` returns the key: the same loud miss as any other non-string leaf.

**Only English declines.** ja and tc have no number agreement; their entries
stay plain strings, byte-identical at every count. Locale parity is asserted
on the bare leaf path (`aiSearch.matchCount`, whatever its shape), and
`translation-keys.spec.ts` derives each locale's permitted member set from
`Intl.PluralRules(...).resolvedOptions().pluralCategories` — en must carry
exactly `one` + `other`, and a pluralized entry in ja or tc is a failure by
construction.

The member names are **reserved words**: a genuine namespace whose keys were
all category names would be read as a plural leaf. None exists; the shape
check names any that appears.

Fifty-two keys carry members today — every key where a count of 1 is
reachable and the sentence has a noun that agrees:
`dashboard.upcomingOlderHidden`, twelve under `transactions.*`
(`resultCountAnnouncement`, `splitPartsDropped`, and ten under
`transactions.select.*`, the select mode's counts of chosen, left-out,
shared and unshared rows), `budget.alertSnackbarMore`,
three under `reports.*`, ten under `settings.*` (preview, import, restore and
delete counts), `aiSearch.matchCount`, fifteen under `import.*`,
`reminders.billDueIn`, two under `recap.*`, four under `insights.*`,
`palette.resultCount`, and `household.overview.showMore`, how many rows the
household list still holds back. Count keys guarded to `> 1`, fed a
compile-time constant, or floored at ≥2 by a detector stay plain strings — if
the guard changes, the key converts then.

The count drifts, because nothing checks it: the shape gate asserts that a
plural entry is *well formed* in every locale, not how many of them there are.
Recount from `en.json` before quoting it.

## How a string gets checked (#260)

`npm run i18n:check` (`scripts/check-i18n.mjs`, a CI step) runs a self-test of
its own parser first, then six scans:

1. **Balanced `t(` calls.** The first argument of every `t(` call is walked
   character-by-character — paren depth, quote state — to the first top-level
   comma or the balanced close, across newlines. Every dot-namespaced quoted
   literal in it must resolve in all three locales; the dot rule keeps a
   ternary's comparison literal (`'expense'`) from being taken for a key. A
   first argument with no key-shaped literal (`t(chip.labelKey)`, template
   literals) is dynamic: counted, never failed. This is what the per-line
   regex could not do — #260 shipped inside a `t(` split across lines with a
   ternary argument, invisible even to a multi-line regex.
2. **Pipe keys.** `'some.key' | translate` stays a line-based scan; a pipe
   whose left side is not an adjacent literal counts as dynamic.
3. **Static `aria-label` and `alt` attributes** — below.
4. **Visible English text nodes** in a template — [below](#visible-english-in-a-template).
5. **An English `Unknown`, `Other` or `User` fallback** in code — [below](#an-english-fallback-in-code).
6. **The widget's own string tables**, their wiring into the iOS build, and
   the widget's Swift — [below](#the-widgets-own-strings).

Beside the scans, one more template check has no number: a translated
fragment joined to a value by a comma — [below](#a-sentence-joined-by-a-comma).

The unit suite adds what the checker cannot see: `translation-keys.spec.ts`
asserts cross-locale parity, plural member shape, non-empty values, and
placeholder parity (union across plural members). Neither gate can check a
dynamic key's existence, and a commented-out call is still counted as a
reference. English hardcoded as *visible text* is caught by scan 4 when a
template's text node holds two words or more, by scan 5 when code falls
back to `Unknown`, `Other` or `User`, and by scan 6 when the iOS widget's
Swift draws a literal of its own. The rest of it — a single word, or English
that reaches the DOM from TypeScript any other way — is caught by nothing but
review and the component specs that pin sentinel translations.

## Accessibility labels (#273)

`aria-label` wins the accessible-name computation outright — a translated
tooltip does not help a screen-reader user if the label next to it is
hardcoded English. The checker rejects any literal `aria-label="…"` under
`src/app` templates. Three forms pass:

```html
[attr.aria-label]="'common.moveUp' | translate"   <!-- the convention -->
[aria-label]="someExpression"
aria-label="{{ 'some.key' | translate }}"
```

An `<img>`'s `alt` reaches a screen reader exactly the same way, so the same
scan covers it, in the same three forms:

```html
[alt]="'settings.profilePhotoAlt' | translate"
[alt]="'receiptImages.imageNumber' | translate: { index: i + 1, total: total }"
alt="{{ 'k.k' | translate }}"
```

with params where the sentence places a number — `receiptImages.imageNumber`
(*Receipt image {{index}} of {{total}}*) is the key the camera dialog's
captured-photo thumbnails reuse, rather than a second key saying the same
thing. The one deliberate difference between the two scans is that an empty
`alt=""` **passes**: it is WCAG's idiom for a decorative image, the way to
say "this picture carries no information, skip it", where an empty
`aria-label` is only ever a mistake.

The convention's model is the upload area's reorder trio in
`file-dropzone.component.html`, which binds each name through the pipe with
the file's place and name,
`[attr.aria-label]="'import.moveFileUpLabel' | translate: { position: i + 1, name: file.name }"`.
A control stamped once per item takes a name that names its item: the
camera's reorder trio still binds the bare `common.moveUp` /
`common.moveDown` / `common.remove`, and `icon-labels:check` freezes those
three as defects ([accessibility.md](accessibility.md)).
The UI-audit harness must never select on label text — it drives the user
menu via `app-header button.user-menu-button`, a class that exists for that
purpose, locale-independent by construction.

## Visible English in a template

The same defect as the labels above, one position over: a sentence written
straight into a text node reads as English on every locale. The checker's
fourth scan reads the text nodes of every template under `src/app` — the
`.html` files **and** the inline `template:` literals in `.ts` files, which is
where ADR 0058's own sweep missed one — and fails a node carrying **two or
more** words in a row.

Two words, not one, because one word is indistinguishable from a product name,
a unit or a stray Material ligature. Before the words are counted, four things
are blanked in place, so line numbers still mean what they say:

| Blanked | Why |
|---|---|
| `<!-- … -->` | a commented-out sentence is not a shipped sentence |
| `{{ … }}` | blanked rather than skipped: a node is routinely mixed content, and the English *between* two interpolations is the part worth seeing |
| `@if (…) {`, `@for (… ; track …) {`, `@empty {` | control-flow headers sit in text position and read as two English words |
| `<mat-icon>…</mat-icon>` bodies | a ligature is markup: `error_outline` is two word-runs, and there are 411 of them across 86 templates — the rule's whole false-positive surface |

A product or file-format name that is spelled the same in every locale would
mean three identical copies in the catalogs, so those live in a named
`PROPER_NOUNS` table in `scripts/check-i18n.mjs` instead — six rows today, each
naming its file, its exact text and its reason. The table is matched on the
text, not on a line number, because a line number rots on the first edit above
it. A row that stops matching anything **fails**: an allowance nobody uses is
an allowance nobody reviews.

What it still cannot see: a single English word; English that reaches the DOM
from TypeScript rather than a template, unless it is one of the three fallback
words scan 5 reads ([below](#an-english-fallback-in-code)); `src/index.html`,
which renders before Angular boots; and a visible attribute that is neither
`aria-label` nor `alt` (`placeholder`, `title`, `matTooltip`).

## An English fallback in code

The same defect again, from the other side of the template: code that falls
back to an English word for a value the catalog cannot name. A category id
the catalog lacks — a deleted category, an id written on another device, a
catalog not loaded yet — read *Unknown* on every locale on five screens and
in five exports, and two more surfaces printed the raw id
([ADR 0180](ADR/0180-a-saved-key-joins-the-wait-and-a-reader-sees-their-own-language.md)).
They all read `common.unknownCategory` now, through the one rule in
`core/utils/category-display.utils.ts`: `categoryDisplayName` for an id,
`categoryNameOrUnknown` for a name that may be missing. *Unknown*, not
*Other*, because *Other* is the catch-all's own name, and an id the catalog
lacks would read as that real category, beside it.

A person with no name is the same defect for a name: an account whose
sign-in named nobody read *User* in every language, and stored it
([below](#a-person-with-no-name)).

The checker's fifth scan fails a **string literal whose whole content is
`Unknown`, `Other` or `User`**, case-sensitive, so a chat message's
`role: 'user'` is not a hit, in every non-spec file under `src/app` except
`core/services/testing/`, whose fixture names a category *Other*:

- A `.ts` file is read with a regex-aware lexer, copied from
  `check-colors.mjs` rather than imported, so a comment never counts and a
  division is not taken for a regex. A string inside a `${…}` substitution
  is read too, so `` `${name ?? 'Unknown'}` `` counts.
- An inline `template:` is read as scan 4 reads it, and a `.html` file the
  same way, with `<!-- -->` comments masked and offsets kept, so the
  reported line is the real one.
- Only the word alone matches. `'Unknown error'`, a key such as
  `settings.platformUnknown` and prose such as the receipt prompt's
  `merchant="Unknown"` default do not.

Two kinds of site keep the word on purpose, and each sits in a table in
`scripts/check-i18n.mjs`, passed into the scan as a parameter
([ADR 0151](ADR/0151-the-frozen-accessibility-findings-are-fixed-and-the-freezes-stay-empty.md)):

| Table | What it holds | Today |
|---|---|---|
| `MODEL_FACING_FALLBACKS` | a missing category named *Other* inside a prompt: the model reads the word, and no screen or export shows it | 3 rows, 3 sites |
| `STORED_FALLBACKS` | *Unknown* written onto a row as its description or merchant when a parse finds none: the word becomes the row's own data, kept by the owner's decision of 2026-10-15 | 5 rows, 6 sites |

A row names its file, the trimmed text of the line, how many hits (fallback
literals) the file's lines of that text hold, and its reason. It is matched
on file and text, never on a line number, for the `PROPER_NOUNS` reason
above, and its hits are counted: two identical lines in
`cloud-llm-provider.base.ts` share one row with `count: 2`. A hit no row
covers is an offence. A row whose count no longer matches, either way, is
drift, and drift fails too, so a row can neither outlive its site nor
quietly cover a second one. That is why the tables are not a freeze:
nothing in them is waiting to be fixed, and each row says why its word
stays. Neither table has a `User` row: no site keeps that word. A live run
prints *Checked 432 files for an English "Unknown", "Other" or "User"
fallback (8 rows allow 9 hits: 3 model-facing for 3, 5 stored for 6).*

What it cannot see: prose that starts with the word (`'Unknown error'`); a
two-word default of the same kind, `'Unknown Merchant'`, which two receipt
readers store as a row's description (`native-receipt.service.ts`,
`receipt-text-parser.ts`), kept by the same decision; another English word
for nobody, such as `Guest`, `Anonymous` or a lowercase `user`, since the
scan knows three; a word assembled from pieces
(`'Unk' + 'nown'`) or read from data, which stands whole in no literal (a
constant that holds it whole fails where it is declared); a single word in a
template's text node (`@else { Unknown }`), which is not a literal and which
scan 4 leaves to review; and markup held in a TypeScript string that is not
an inline template.

### A person with no name

A sign-in provider may name nobody, and the rules let a household member
have no name. Neither is shown as an English word.
`core/utils/person-name.utils.ts` is the one place that decides for the
account holder and the household's members
([ADR 0182](ADR/0182-a-control-reads-in-the-accounts-language-and-date-format-and-nothing-re-provides-materials-adapter-or-words.md)):

| Helper | Reads | For |
|---|---|---|
| `givenName(name)` | the name trimmed, or `''` | anything that stores a name for others to see: a household member's document |
| `accountDisplayName(name, t)` | the name, or `common.unnamedAccount` (*No name set*, 名前未設定, 未設定名稱) | the header and the settings card |
| `memberDisplayName(name, t, form)` | the name, or `household.unnamedMember` (*A member*) and, mid-sentence, `household.unnamedMemberInline` (*a member*) | the member chips, the member list and its removal sentences |
| `welcomeGreeting(name, t)` | the name's first word in `common.welcomeNamed`, or `common.welcome` with no name | the dashboard's greeting |

The household setup page's invite list reads none of them: it shows the
invite's `inviterName`, which the invite callable takes from the caller's
token, as given, and hides its *Invited by* line when that name is empty.

The words are never stored, so a language switch changes them everywhere at
once. A sign-in that names nobody stores `''` as the profile's
`displayName`, and a member who gave no name is stored with `''` too. A
profile that already stores `'User'` keeps it: it is a name like any other,
and the greeting reads *Welcome back, User*. The parameter is named `t` so
scan 1 reads the keys each helper passes it.

## A sentence joined by a comma

`{{ 'common.welcome' | translate }}, {{ userName() }}` is a sentence only
English can punctuate: the comma sits in the template, where no language can
move it, while ja writes `、` and puts `さん` after the name, and tc writes
`，`. Such a sentence is one key with a placeholder, which each language
punctuates itself: `common.welcomeNamed` is *Welcome back, {{name}}*,
おかえりなさい、{{name}}さん and 歡迎回來，{{name}}.

`i18n:check` fails a translated interpolation followed by `,` or `、` and
then another interpolation, in every template under `src/app`, inline
`template:` strings included, with comments masked; the line reported is
the comma's own. A live run prints *Checked 103 templates for a translated
fragment joined to a value by a comma.* The dashboard's greeting was the one
site.

A **colon** is accepted by decision: `label: value` reads correctly in ja
and tc, which write it on the about page, the profile example, the import
errors and the budget alert. What the check cannot see: a full-width `，`
or a dash between the two; a join with a word between them (scan 4 reads the
word if it is English); a comma that ends the element before the value
begins; and a sentence assembled in code, `t('a.b') + ', ' + name` or a
template literal.

## Material's own words

Material's components carry English words of their own, which a page never
writes and the scans above never see: a datepicker's toggle and calendar
buttons, a stepper's hidden state words, a sortable header's description.
Each is read from the catalog
([ADR 0182](ADR/0182-a-control-reads-in-the-accounts-language-and-date-format-and-nothing-re-provides-materials-adapter-or-words.md)):

| Component | Where the words come from | Keys |
|---|---|---|
| Datepicker | `AppDatepickerIntl`, provided once at the root by `provideAppDatepicker()`; it relabels whenever the date adapter follows the reader, then tells open calendars to redraw | `datepicker.*` |
| Stepper | `AppStepperIntl`, provided by the import wizard (`APP_STEPPER_INTL_PROVIDER`), so Material's stepper stays in the wizard's lazy chunk; it relabels on every catalog | `stepper.completed`, `stepper.editable`, `stepper.optional` |
| Sort header | `[sortActionDescription]="'transactions.sortBy' \| translate"` on each sortable column | `transactions.sortBy` |

Both intl classes **assign** their fields: Material declares them as class
fields, which would shadow a getter on the subclass. In the import wizard a
finished step that is not the selected one is editable, so a reader hears
`stepper.editable` (編集可能 in ja); `stepper.completed` is heard only while
an import is being written.

`material-intl.spec.ts` is the pin: it resolves both intl classes over the
real `TranslationService` with the ja catalog loaded and fails on any string
field still equal to Material's English, bar `calendarLabel`,
`startDateLabel` and `endDateLabel`, which nothing in Material 22.1.4 reads.
A sortable header is held by lint: the `.html` block's `no-restricted-syntax`
fails an element carrying `mat-sort-header` without a **bound**
`sortActionDescription`, since a static one is one language for every
reader. A component that brings Material's datepicker module back would
bring its English labels with it, so that module is banned too
([locale-formatting.md](locale-formatting.md#what-a-datepicker-shows-and-reads)).

### A word is read where it is shown

A word in the reader's language is translated where it is shown, never once
and kept: through the translate pipe in the template, which keys its memo on
the locale and the catalog version, or by `t()` inside a `computed` that the
catalog drives. A field initializer runs once, when the instance is built,
and a value a subscription stored stays as it was found; neither hears a
language switch. ADR 0182's second browser run met both. The Settings page's
Date Format select named *Automatic* by `t()` in a field initializer, so
after a language picked on the page it stayed in the language the page
opened in, while Currency's options, translated in the template, followed:
Material's option re-reads its own text after every check and the select
redraws its trigger. The option now carries `settings.dateFormatAuto` and the
template translates it. And the transaction list's insight chips named their
category in the Firestore subscription that found them; `chips` is now a
`computed` over what the analysis found, reading `categories()` and
`translationsVersion()`, so a switch renames a chip without analysing again.

No gate fails either shape: whether code that translates runs once or on
every switch is not a question a syntax check can answer, in a field, a
constructor, `ngOnInit`, a subscription or a signal `set`. A spec that
switches the catalog (`createTranslationStub`'s `translationsVersion`, with a
`t` whose output moves) is what holds them, and a live switch in the browser
is what finds them (journey 101's steps 4 and 6).

## The widget's own strings

The iOS widget ([widget.md](widget.md)) draws what the app wrote into its
snapshot, already translated, with one exception: its own name. The widget
gallery shows that name before the app has ever run, so it cannot come from
the snapshot or from the account; iOS reads it from string tables in the
widget extension, by the device's language
([ADR 0183](ADR/0183-the-widget-reaches-the-lock-screen-opens-the-dashboard-names-itself-in-the-devices-language-and-follows-the-accounts-language-currency-and-hidden-cards.md)). The catalogs never
reach those tables, so the sixth scan holds the two together.

`NATIVE_TABLES` maps each `.lproj` language to the catalog it mirrors:

| Table | Catalog |
|---|---|
| `ios/App/HomeAccountWidget/en.lproj/Localizable.strings` | `en` |
| `ios/App/HomeAccountWidget/ja.lproj/Localizable.strings` | `ja` |
| `ios/App/HomeAccountWidget/zh-Hant.lproj/Localizable.strings` | `tc` |

A device language with no row reads the `en` table, the development
region's. That includes `zh-Hans`, which the web maps to `tc` with every
other `zh*` tag ([above](#which-language-a-session-speaks)): a Simplified
Chinese device reads the widget's name in English.

The scan has four parts:

- **A strict `.strings` parser.** Comments, whitespace and
  `"key" = "value";` entries only: both sides quoted, a string on one line,
  the escapes `\"`, `\\`, `\n`, `\t` and `\r`, each key once. Xcode's own
  reader is laxer (unquoted words, any escape), and a laxer reader here
  could pass a table the device reads differently. Reading stops at the
  first problem, reported with its line.
- **The tables against the catalogs.** Every catalog has a row and every
  row a catalog; every table holds the `en` table's keys exactly. Each key
  names a string in the catalog its language mirrors, not a plural or a
  namespace, and the value is that string, word for word. A missing table, a
  language `NATIVE_TABLES` does not map, an unknown key and a mismatch each
  fail.
- **The wiring.** A table on disk reaches the built widget only through
  `project.pbxproj`: a `Localizable.strings` variant group copied by the
  `HomeAccountWidget` target's own Resources phase, a file per language
  inside it, and each language in the project's `knownRegions`. A table
  that is not wired is never copied, and the device shows the key itself.
  The scan reads the project file as a property list and walks the target's
  own phases, so a group only another target copies does not count.
- **The Swift's display literals.** A string literal standing first after
  `Text(`, `Label(`, `LocalizedStringKey(`, `NSLocalizedString(`,
  `String(localized:`, `.configurationDisplayName(`, `.description(` or
  `.accessibilityLabel(`, or a `LocalizedStringKey` declared with `{` or
  `=`, fails unless it is a key of the `en` table. An interpolated literal,
  and `Text(verbatim:)`, which iOS never looks up, fail either way. A type
  head needs an identifier boundary before it, so `UILabel(` and
  `RichText(` are not heads while `SwiftUI.Text(` is. Comments are masked
  by a Swift lexer that follows nested block comments, raw strings and
  interpolation.

Today the tables hold one key, `app.title`. `HomeAccountMonthWidget.appName`
reads it for the gallery, and for the face a placed widget draws with no
file to read. The live run prints:

```
Checked the widget's string tables (en for en, ja for ja, zh-Hant for tc) against the catalogs and their wiring in ios/App/App.xcodeproj/project.pbxproj, and 2 widget Swift files for display literals.
```

What scan 6 cannot see:

- **A word that is not a literal.** `Text(labels.net)` draws a string the
  app wrote into the snapshot, already translated; a `LocalizedStringKey`
  held in a variable is read where it is declared.
- **A head the list does not name**: `Button("…")`, `Toggle`,
  `.navigationTitle`, a function declared `-> LocalizedStringKey`.
- **A literal that is not the first thing after its head**: a conditional
  of literals, `Text(isLocked ? "Locked" : "Signed out")`; an optional key,
  `let name: LocalizedStringKey? = "Home"`; and
  `LocalizedStringKey(stringLiteral: "Home")`.
- **Swift outside the top level of the widget's folder**: a subfolder of
  it, the Share Extension and the app's own shell, and an `Info.plist`
  display name (the app's *HomeAccount* is English on every device).
- **Which group holds the variant group.** A variant group under another
  group points its tables at the wrong folder, which the build reports, not
  the scan.
- **A catalog placeholder.** A `{{name}}` copied into a table equals the
  catalog, and iOS shows it as written; the one key has none.

## Summary

| Escape route | What closes it | Where |
|---|---|---|
| Key referenced that no locale defines | balanced `t(` + pipe scans | `npm run i18n:check`, CI |
| Key in one locale, missing in another | path parity | `translation-keys.spec.ts` |
| English plural forced on a count of 1 | plural objects, en only | `t()` + the converted keys |
| Plural members malformed or misplaced | per-locale CLDR shape check | `translation-keys.spec.ts` |
| Placeholder added to en alone | placeholder parity (member union) | `translation-keys.spec.ts` |
| Hardcoded `aria-label` or `alt` | static-attribute scan (`alt=""` allowed) | `npm run i18n:check`, CI |
| Hardcoded *visible* English text | text-node scan, two words or more | `npm run i18n:check`, CI |
| A proper-noun allowance outliving its text | `PROPER_NOUNS` staleness check | `npm run i18n:check`, CI |
| An English `Unknown`, `Other` or `User` fallback in code | whole-literal scan; two tables of rows with counts, the model-facing and the stored words, and a drift check on each row | `npm run i18n:check`, CI |
| A translated fragment joined to a value by a comma | comma-join check (a colon is accepted) | `npm run i18n:check`, CI |
| A person with no name shown as an English word | `person-name.utils.ts`, and the `User` word in scan 5 | `npm run i18n:check`, CI + `person-name.utils.spec.ts` |
| Material's own English (datepicker, stepper) | the app's intl classes; a pin on every own string field | `material-intl.spec.ts` |
| A widget string table drifting from its catalog, or left unwired | scan 6: a strict `.strings` parser, every table against the catalog it mirrors, the tables' wiring in `project.pbxproj` | `npm run i18n:check`, CI |
| A literal the iOS widget draws itself | scan 6's Swift display-literal check | `npm run i18n:check`, CI |
| A sortable header described in English | `mat-sort-header` without a bound `sortActionDescription` fails | `npm run lint`, CI |
| A translation stored once (a field, a constructor, a subscription, a signal `set`) | nothing automatic | review + a spec that switches the catalog |
| Checker's own parser drifting | 153-case `--self-test` | chained into `i18n:check` |
| Any other English reaching the DOM from TypeScript | nothing automatic | review + sentinel specs |

## When you add another string

**A new user-facing string?** Give it a key in all three files — parity fails
on a partial add — and bind it with `| translate` or `t()`. If it names a
control only assistive tech hears, it is an `[attr.aria-label]` binding, not
an attribute; if it describes an image, it is a `[alt]` binding, unless the
image carries no information at all, in which case it is `alt=""`.

**A value the catalog may not name?** A category goes through
`categoryDisplayName` or `categoryNameOrUnknown`, which read
`common.unknownCategory`; a person's name goes through
`person-name.utils.ts`; anything else gets a key of its own. A literal
`Unknown`, `Other` or `User` fails scan 5. A word stored on a row, or read
only by a model, needs a row in its table, with its reason.

**A word the iOS widget draws itself?** A catalog key, and a line in each
of the widget's three tables with the catalog's value, in one commit. A
fourth table needs its `NATIVE_TABLES` row and its wiring in
`project.pbxproj` too. A word the snapshot can carry stays in the catalogs
alone, composed on the web ([widget.md](widget.md)).

**A sentence with a value in it?** One key with a placeholder, never a
translated fragment and a value side by side: the language places the value
and its punctuation.

**A new counted string?** Ask two questions before pluralizing: can the count
actually be 1 (check the guard), and does the English sentence have a noun
that agrees? Both yes → en gets `{ "one": …, "other": … }` with `{{count}}`
in both members; ja and tc get one plain string each. Either no → three plain
strings.

**A new `t()` call?** Write the key as a literal in the first argument if you
can — the checker validates it wherever the line breaks fall. A computed key
is invisible to every gate; if you must, add a spec that resolves it against
the real catalogs, the way `insight-card.utils.spec.ts` does.

**Removing or renaming a key?** `i18n:check` lists every referencing site,
including commented-out ones. Rename in all three files and every site in one
commit; the gates fail on anything left behind.
